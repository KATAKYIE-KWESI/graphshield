# 🛡️ GraphShield

A graph-native **gatekeeper agent** that stops software supply-chain attacks before a malicious release reaches production.

**Track:** Agents That Act on Connected Data (also entering: Agent Memory and Coordination)

## The problem

Apps pull in hundreds of transitive dependencies. Attackers look for a small, deep utility package with an inactive maintainer, take the account over (or get added as a "helpful" co-maintainer), and push a poisoned version that thousands of apps install automatically. Examples: `event-stream` (2018) and `xz-utils` (2024).

## What GraphShield does

Each new release triggers the **Gatekeeper agent**, which reasons over the registry graph in FalkorDB:

1. **Identify** who published what.
2. **Score maintainer trust**: account age, verification, MFA, and how long they have maintained *this* package.
3. **Propagate trust**: do established, verified maintainers vouch for this account through co-maintainership on *other* packages?
4. **Compute the blast radius**: walk `DEPENDS_ON*1..5` upstream to count every package and app that would pull in this version.
5. **Trace the attack paths**: the deepest app → … → package chains.
6. **Recall memory**: earlier decisions about this maintainer or package.
7. **Decide and record**: `ALLOW` / `QUARANTINE` / `BLOCK`, written back into the graph as a `:Decision` node linked to its evidence.

Every step keeps the Cypher it ran, its parameters, the server run time and the rows returned, so **every verdict can be traced** to the graph facts behind it.

The Gatekeeper is deliberately deterministic: the same graph facts always give the same verdict.

### Investigator agent (LLM)

`BLOCK` and `QUARANTINE` decisions are left open in the graph (`needs_investigation: true`). The **Investigator agent** (`graphshield/investigator.py`) picks them up and investigates. It runs on any OpenAI-compatible LLM API, and all the supported providers have a free option: Groq (default, `openai/gpt-oss-120b`), Google Gemini, Hugging Face, or a local Ollama model.

- It explores the graph by **writing its own Cypher**, run through `GRAPH.RO_QUERY`, so FalkorDB itself rejects any write.
- It looks for the wider campaign: what else the account can publish, packages staged for a follow-up, earlier flags, and exposed apps.
- It can **flag** an account through one narrow write tool, `flag_maintainer`.
- It ends by calling `submit_report`, which writes an `:Investigation` report (severity, findings, packages at risk, recommended actions) linked to the decision and to the accounts it flagged.

### Coordination through the graph

The two agents never call each other. They coordinate through shared graph state:

```
Gatekeeper   -> (:Decision {needs_investigation: true})
Investigator -> reads open decisions, writes (:Investigation)-[:INVESTIGATED]->(:Decision),
                sets Maintainer.flagged and links (:Investigation)-[:FLAGGED]->(:Maintainer)
Gatekeeper   -> reads Maintainer.flagged on that account's next release (+30 risk, cites the reason)
```

Every Investigator tool call is traced the same way as the Gatekeeper's steps.

## Graph data model

```
(:Maintainer {handle, created_at, last_active_at, verified, mfa})
    -[:MAINTAINS {since}]->  (:Package {name, kind: 'app'|'library', tier, weekly_downloads})
    -[:PUBLISHED {at}]->     (:Version {id, number, published_at, has_install_script, status})

(:Version)-[:PART_OF]->(:Package)
(:Package)-[:DEPENDS_ON]->(:Package)          // dependent -> dependency

(:Decision {id, verdict, risk, impact, reasons, at, needs_investigation})
    -[:EVALUATED]->(:Version)
    -[:CITED]->(:Maintainer), (:Package)      // the agent's memory + evidence

(:Investigation {id, severity, headline, summary, findings, actions, packages_at_risk, model, at})
    -[:INVESTIGATED]->(:Decision)
    -[:FLAGGED]->(:Maintainer)                // sets Maintainer.flagged / flag_reason
```

`Version.prev_active_at` records when the publisher was last active *before* that release, which is how the Gatekeeper spots a dormant account that suddenly wakes up.

Timestamps are epoch milliseconds, so they compare directly with Cypher `timestamp()`.

Seed data (synthetic, generated by `graphshield/seed.py`): 5 core utilities → 15 libraries → 30 frameworks → 100 apps, 41 maintainers and about 370 versions. `left-pad-core` is a deep utility with one old, inactive maintainer and no MFA.

## Cypher the product depends on

All queries are in [`graphshield/queries.py`](graphshield/queries.py). These are the core ones:

**Blast radius (variable-length traversal)**
```cypher
MATCH (dep:Package)-[:DEPENDS_ON*1..5]->(t:Package {name: $pkg})
WITH collect(DISTINCT dep) AS deps
RETURN size(deps) AS total_dependents,
       size([d IN deps WHERE d.kind = 'app']) AS apps_affected,
       reduce(s = 0, d IN deps | s + d.weekly_downloads) AS weekly_downloads_at_risk
```

**Trust propagation via co-maintainers**
```cypher
MATCH (m:Maintainer {handle: $handle})-[r:MAINTAINS]->(p:Package)<-[:MAINTAINS]-(peer:Maintainer)
WHERE p.name <> $pkg AND peer.handle <> m.handle
  AND timestamp() - r.since > 90 * 86400000
  AND peer.verified = true
  AND timestamp() - peer.created_at > 365 * 86400000
RETURN count(DISTINCT peer) AS vouching_peers
```

**Attack paths**
```cypher
MATCH path = (a:Package {kind: 'app'})-[:DEPENDS_ON*1..5]->(t:Package {name: $pkg})
RETURN [n IN nodes(path) | n.name] AS chain, length(path) AS hops
ORDER BY hops DESC LIMIT 5
```

**Agent memory (write and recall)**
```cypher
MATCH (m:Maintainer {handle: $handle})-[:PUBLISHED]->(v:Version {id: $vid})-[:PART_OF]->(p:Package)
CREATE (d:Decision {id: $did, verdict: $verdict, risk: $risk, impact: $impact,
                    reasons: $reasons, at: timestamp()})
CREATE (d)-[:EVALUATED]->(v), (d)-[:CITED]->(m), (d)-[:CITED]->(p)
SET v.status = $status
```

### Scoring

| Signal | Risk |
|---|---|
| Account < 30 days old (or < 90) | +35 (+15) |
| Not verified / no MFA | +10 each |
| Maintainer of this package for < 30 days | +15 |
| No vouching peers (co-maintainership must be > 90 days old) | +10 |
| Account dormant ≥ 180 days before this release (possible takeover) | +20 |
| Version adds an install script | +15 |
| Publisher flagged before (memory) | +20 |
| Account flagged by the Investigator agent | +30 |

Impact comes from the blast radius: ≥ 50 apps is **critical**, ≥ 10 is **high**.
**BLOCK** if risk ≥ 50 and impact is high or critical. **QUARANTINE** if risk ≥ 50, or risk ≥ 30 and impact is critical. Otherwise **ALLOW**.

## Setup

Requirements: Python 3.10+ and Docker (or a FalkorDB Cloud instance).

```bash
docker compose up -d                 # FalkorDB on :6379, browser UI on :3000
python -m venv .venv
.venv\Scripts\activate               # Windows   (macOS/Linux: source .venv/bin/activate)
pip install -r requirements.txt
python -m graphshield.seed           # load the synthetic registry
streamlit run app.py
```

To enable the Investigator agent, copy `.env.example` to `.env`, pick an `LLM_PROVIDER`, and paste that provider's free API key (for Groq: https://console.groq.com/keys). Everything else works without it.

To use FalkorDB Cloud, set `FALKORDB_HOST`, `FALKORDB_PORT`, `FALKORDB_USERNAME` and `FALKORDB_PASSWORD` (see `.env.example`).

## Demo

1. Click **Seed / reset registry**.
2. Click **✅ Legit release**: an established maintainer ships a patch, and the Gatekeeper returns **ALLOW**.
3. Click **🚨 New-account attack**: a 2-day-old, unverified account is added to `left-pad-core` and publishes a version with an install script. The Gatekeeper returns **BLOCK**, shows that all 100 apps would be affected, and lists every query it ran with its timing.
4. Click **🔎 Investigate this case**. The Investigator writes its own Cypher and finds that the same account was also quietly granted access to `tiny-utf8`. It flags the account and files a report.
5. Click **🔁 Attacker strikes `tiny-utf8`**. The Gatekeeper blocks it and cites the Investigator's flag: the two agents coordinated through the graph.
6. Reset, then click **🕵️ Account takeover**: the trusted maintainer of `left-pad-core`, dormant for 700 days with no MFA, suddenly ships an install script. There's no new account, but the Gatekeeper still returns **BLOCK** on dormancy, missing MFA, no vouching and the install script.

## Why a graph

The core question, "who transitively depends on this, through any number of hops?", is a variable-length path traversal. In FalkorDB that is a single `-[:DEPENDS_ON*1..5]->` pattern evaluated over adjacency matrices. In SQL it needs a recursive CTE whose cost grows with every join level. Trust propagation and agent memory are graph patterns as well. Remove FalkorDB and the agent has nothing to reason over.

## Architecture

```
graphshield/
  db.py            FalkorDB connection (env-configured)
  queries.py       every Cypher query used
  seed.py          synthetic registry generator
  simulate.py      publish-event injector (attack / takeover / repeat / legit)
  agent.py         Gatekeeper agent: traced steps → score → Decision node
  investigator.py  Investigator agent (LLM): own Cypher → flags → Investigation node
app.py         Streamlit UI (pyvis blast-radius view, agent trace, decision log)
```

## Data

All data is synthetic, generated by `seed.py`. No real package, maintainer or personal data is used.
